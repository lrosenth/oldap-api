# Interactive read baseline — 2026-09-29

## Decision supported by this baseline

The first optimization should target oldaplib model reconstruction and Redis connection reuse. On the existing warm local data, ordinary resource reads and summaries spend most of their time preparing the resource factory, not executing their main GraphDB query. A Flask-to-FastAPI migration or GraphDB Enterprise purchase is not supported as the first remedy for this measured single-request bottleneck. Neither option has been benchmarked here.

### The cache is the main source of repeated work

The supplement separates Redis commands from cache materialization. For a medium, mean total time is 580.7 ms:

| Non-overlapping bucket | Mean ms | Interpretation |
|---|---:|---|
| Redis commands | 384.4 | 563 commands; includes new connection setup and client/server round trips |
| Redis client initialization | 29.0 | 1,126 initializations: cache client plus writer-isolation-check client |
| Cache get exclusive remainder | 107.9 | Python reconstruction/decoding after subtracting nested measured calls |
| Project.read exclusive remainder | 35.4 | Repeated project handling outside its measured children |
| GraphDB HTTP | 15.3 | Three query calls, including engine wait/evaluation and response transfer |
| Other measured/unmeasured request work | 8.7 | Authentication, result processing, JSON, harness and remaining small buckets |

The separate CPU profile of a media read records approximately 4.0 million function calls, 11,204 serializer decoder-hook invocations, 524 Project.read calls, 343 PropertyClass constructions, 59 ResourceClass constructions and 563 Redis `_connect` calls. Profiled wall times are inflated by cProfile and are **not** baseline latencies.

The code explains this pattern:

1. `ResourceInstanceFactory.__init__` resolves the project and Shared data models.
2. `CacheSingletonRedis.get` decodes JSON into full domain objects using `serializer.make_decoder_hook(connection=...)`.
3. Property/resource constructors repeatedly resolve projects, superclass models and the base Thing class while reconstructing that graph of objects.
4. `Project.read` repeatedly constructs `CacheSingletonRedis`. Despite its name, this class is not a shared singleton/pool; each construction creates a fresh redis-py client/pool.
5. With archive coordination enabled, each cache construction also creates a temporary Redis client to validate writer-store separation. Here the distinct database numbers avoid a writer Redis network call; the protective check itself must remain intact.

### Model endpoints are also part of normal user workflows

SALSAH `src/lib/resources/client.ts` calls `/admin/datamodel/{project}` while building resource cards and loads project/Shared models for resource views. Therefore these GETs belong in user-path performance analysis despite their `/admin` prefix. FasnachtsPage archive image selection uses structured Lucene field filters and summaries; its field-search variant was measured separately.

Fasnacht model retrieval averages 491.6 ms in the instrumented supplement: four GraphDB calls total 142.0 ms, 327 Redis commands total 184.9 ms, and remaining time is model construction/decoding/serialization. Shared averages 177.6 ms, with 57.6 ms GraphDB and 53.2 ms Redis. There is useful GraphDB work here, but it still does not explain the whole response time.

The administrative model route intentionally uses `ignore_cache=True` after a prior stale-model recovery bug. Do not remove this guarantee simply to make the benchmark faster. A lightweight, versioned UI model representation can be evaluated separately while retaining authoritative fresh administrative reads.

## Recommended next step, in order

1. **Reuse Redis clients/connection pools at the appropriate process/configuration boundary.** Retain cache/writer separation checks, correct fork/thread lifecycle, endpoint identity and bounded pools. Validate that connection setups per request fall sharply. This is the smallest concrete candidate addressing the largest measured time bucket.
2. **Remove repeated project/model reconstruction within a request.** Reuse resolved project objects and superclass information; avoid constructors recursively re-reading the same cached metadata. Measure the 524/563 counters before and after. A full new cache architecture is not required as the first change.
3. **Then evaluate a reusable read-only model snapshot and UI model delivery.** If needed, separate immutable schema metadata from request-specific connections, permission state, mutation tracking and callbacks. Define revision/invalidation semantics. Never share an entire mutable, user-bound factory globally.
4. **Keep batches and avoid extra UI metadata fetches.** The summary route already amortizes the large fixed factory cost across resources. Search property projection is inexpensive here, but is not interchangeable with complete typed summaries and media authorization.
5. **Repeat this exact baseline before concurrency tests.** Only then measure the Free-edition queue/concurrency boundary and compare Enterprise/core counts. FastAPI remains a separate experiment after library/cache work; the current findings do not identify Flask dispatch as the dominant cause.

No percentage improvement is promised: the largest measured bucket includes unavoidable Redis work as well as avoidable setup. One change at a time with the same catalog will establish actual gains.

## Limits and follow-up questions

- This is a small local dataset and a warm serial benchmark, not an HMB sizing exercise. No concurrent-user capacity, throughput ceiling, large-data behavior or Enterprise benefit has been measured.
- Fixed queries/objects expose repeated work but do not represent the frequency mix of real sessions. No browser rendering, image download, IIIF transformation or WAN latency is included.
- GraphDB HTTP timings include queueing, engine evaluation and transfer. No query-plan timing, engine-only attribution or JMX sampling was enabled. CPU/RAM monitor snapshots are inventory, not a sustained resource utilization study.
- `live_http`, `inprocess` and `instrumented` run sequentially; differences cannot be interpreted as pure Flask/server overhead. Some first-use parser/import effects, OS scheduling and Python garbage collection contribute to variation.
- The running service and isolated process use normal shared cache population. No true cold-cache experiment was performed. The globally clearing `create_app()` startup path was deliberately avoided.
- No live permissions/data were modified. The fingerprint check detects concurrent changes but does not provide a transactionally isolated snapshot; it covers explicit named graphs, not arbitrary external state.
- Existing model endpoints print ontology debug data; the benchmark does not change this behavior. These prints are visible in local logs but no credentials or tokens are written by the diagnostic.
