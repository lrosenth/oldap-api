# Mixed-reader concurrency test — 2026-09-30

## Decision

The next experiment should compare **1, 2 and 4 API worker processes with the
same Flask implementation**. At 16 active readers, the current single-process, threaded
Werkzeug deployment consumes 98% of one CPU core, throughput scaling flattens,
and request p95 reaches 1.07 seconds. GraphDB consumes 60% of one core and Redis
1.4%. This strongly suggests API-process CPU saturation as the first constraint
for this workload. It does not prove that GraphDB has no internal queue or that
additional workers will scale linearly.

## Measurements

Native API v0.2.28, optimized unpublished oldaplib 0.7.22, CPython 3.13.9 with
GIL enabled, GraphDB Free 11.5.1, M5 Max/18 cores/36 GiB. Services were neither
restarted nor reconfigured. The API is **one process with request threads**.

Each stage offers new workflows for 60 seconds, then drains; measured duration
is approximately 62 seconds. CPU percentages use 100% for one core, not the
whole machine. All values below concern live HTTP requests.

| Active readers | Requests | Requests/s | Request p95 | API CPU | GraphDB CPU | Redis CPU |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 80 | 1.30 | 186 ms | 14.9% | 13.9% | 0.2% |
| 2 | 161 | 2.60 | 208 ms | 24.1% | 20.9% | 0.3% |
| 4 | 301 | 4.88 | 281 ms | 38.9% | 31.2% | 0.6% |
| 8 | 589 | 9.57 | 412 ms | 64.6% | 46.5% | 0.9% |
| 16 | 872 | 14.19 | 1,074 ms | 98.1% | 59.6% | 1.4% |
| 1, recovery | 80 | 1.30 | 254 ms | 15.1% | 14.1% | 0.2% |

Doubling readers from 8 to 16 increases throughput by only 48%, while p95
increases by 2.6 times. There were at most 14 overlapping client HTTP requests
in the 16-reader stage: active readers include people in their think interval.
The load client itself used only 4.4% of one core at this stage.

All **2,083 measured requests** returned HTTP 200 and matched their reference
content. No overload stop threshold was triggered. Recovery throughput and CPU
returned to baseline levels; recovery median was 115 ms versus 129 ms initially.
Recovery p95 was higher (254 versus 186 ms), so tail latency did not reproduce
exactly. These are short samples, not a long-running stability test. API sampled
RSS rose from about 110 MiB initially to a peak of 184 MiB at 16 readers; this
alone neither demonstrates nor excludes a memory leak.

### Where latency grows

At 16 readers, search remains relatively quick; object/model reconstruction and
metadata paths are more affected:

| Reference endpoint | Samples | Median | p95 |
|---|---:|---:|---:|
| Sorted search | 175 | 101 ms | 261 ms |
| Structured full-text search | 60 | 87 ms | 256 ms |
| Archive children | 115 | 91 ms | 221 ms |
| Medium resource | 176 | 552 ms | 1,086 ms |
| 25 resource summaries | 175 | 717 ms | 1,115 ms |
| Linked archive resource | 115 | 737 ms | 1,211 ms |
| Fasnacht datamodel | 28 | 935 ms | 1,282 ms |

A complete search-plus-summaries workflow has p95 **1,247 ms**; archive
navigation (children plus linked resource) has p95 **1,288 ms**. Workflow times
exclude think intervals. The previous serial profile already identified model
reconstruction, deepcopy and repeated serializer inspection as remaining Python
costs. Together with process CPU saturation, this makes those costs plausible
contributors; this run does not individually profile them under concurrency.

## Next bounded implementation and experiment

1. **Make worker startup safe.** `oldap_api/__init__.py:create_app()` currently
   unconditionally calls `CacheSingletonRedis.clear()`. The WSGI entry point
   invokes this in each independently initialized worker. Separate intentional
   cache invalidation from worker lifecycle before adding workers; preserve a
   documented explicit invalidation path for model/deployment changes. Verify
   cold-worker prefix initialization with an existing bearer token, without
   relying on a login having reached that particular worker. Do not share
   mutable Connection/model objects across requests or workers.
2. **Compare Gunicorn with 1, 2 and 4 workers**, holding workload, runtime,
   thread settings, data and warmup constant. First establish a one-worker
   Gunicorn baseline to distinguish server changes from process count. Gunicorn
   is already a pinned dependency; Docker specifies four workers, while local
   `make run-prod` specifies one. These configurations were not exercised here.
   Measure GraphDB queues and per-process memory as well as latency/throughput;
   Redis pool bounds apply per process. Select the smallest useful worker count.
3. **Then optimize per-request CPU** if targets remain unmet: profile serializer
   signature inspection and independent model snapshot reconstruction. Reuse
   immutable metadata where justified, with permission isolation and mutation
   tests. Avoid caching whole permission-dependent responses as a shortcut.

Flask documents Gunicorn worker configuration in its
[deployment guide](https://flask.palletsprojects.com/en/stable/deploying/gunicorn/).
The Python documentation explains why CPU-bound Python threads compete within
a normal GIL-enabled process in its
[threading guide](https://docs.python.org/3.13/library/threading.html).

This evidence does not establish a performance benefit from FastAPI or async.
Those require a separate controlled comparison; async does not remove the
measured Python computation. Similarly, an Enterprise purchase/core count
cannot be justified from this small warm dataset alone. Larger representative
HMB data and database queue/query measurements remain necessary.

## Workload, preservation and reproducibility

The primary subject is anonymous `UnknownUser`. Sixteen independent HTTP
sessions receive normal anonymous access tokens before timing. No administrator
traffic, writes, refresh sessions, media downloads or browser rendering are
included. Fixed reference workflows are 30% sorted search + 25 summaries,
30% medium opening, 20% archive navigation, 10% structured full text, 5%
datamodel retrieval, and 5% hierarchical-list retrieval. Each reader thinks
0.5–1.5 seconds between workflows. Finite stages only approximate these shares.
Datamodel/list reads are consumer metadata, not administrative mutations.

This is a deterministic **closed-loop hot-read test**. Resources and search
terms are fixed; summaries replay their stored reference IRIs instead of using
current search results. Arrays are normalized as unordered for content checks,
so result ordering is not verified. Process CPU includes other service activity
and JVM housekeeping; monitoring is not per-request engine attribution. There
is no direct GraphDB queue measurement in this run. A single ascending ramp
cannot establish statistically stable capacity, multi-hour behavior or an SLA.

The explicit named-graph fingerprint remained exactly unchanged, also matching
the previous baseline: **52,471 bindings**, SHA-256
`ebaaeac52dc4309166aa17747a71b6a566d51ffe8aa7d86cf078d520751eaaa4`.
Normal cache population was allowed; no RDF updates or cache clearing occurred.
No application/library/runtime configuration was changed for this test.
