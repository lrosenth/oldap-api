# Separate Gunicorn worker comparison — 2026-09-30

## Result and decision

Two workers substantially reduce contention in the current hot-read workload.
Four workers improve tail latency further, with a smaller throughput gain and
higher memory use. This supports a **two-worker starting point for a VM pilot**,
with four workers as the next option if response-time targets justify it. The
user's VM has eight vCPUs; these laptop results do not predict its capacity.
GraphDB and the API must share available CPU if colocated on that VM.

At 16 active anonymous readers:

| Gunicorn workers | Requests | Requests/s | Median HTTP | HTTP p95 | API CPU, one-core units | GraphDB CPU | Peak summed API RSS |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 460 | 14.46 | 378 ms | 783 ms | 93.7% | 63.4% | 176 MiB |
| 2 | 583 | 18.26 | 116 ms | 443 ms | 123.2% | 79.4% | 292 MiB |
| 4 | 619 | 19.35 | 99 ms | 306 ms | 128.9% | 86.1% | 490 MiB |

Compared with one worker, two workers increase throughput by **26%** and reduce
p95 by **43%**. Four workers improve throughput by a further **6%** and reduce
p95 by another **31%** compared with two. CPU above 100% means work is running
across more than one core; it is not the percentage of the entire laptop.
Summed RSS includes the Gunicorn master and workers and can double-count shared
pages; it is not unique resident memory. The table's memory peaks are within the
16-reader stage, not the earlier warmup peak (about 510 MiB for four workers).

At eight readers, request p95 is 407 / 282 / 271 ms for 1 / 2 / 4 workers.
Single-reader medians stay near 112–115 ms across configurations and recovery.
This is primarily a concurrency improvement, not a reduction in individual
request CPU cost. Under 16 readers, the two workers handled 291/292 requests;
four handled 118/152/157/192 requests. Keepalive distribution is not perfectly
balanced, but all workers participated. Existing API peer CPU remained about
3.6–4.2% of one core; the load client was below 3% during these stages.

All **2,830 timed requests** returned HTTP 200 and matched their references.
All eight normalized preflight content hashes also match across configurations.
All seven tested worker processes (1 + 2 + 4) served every reference case using
an already-issued bearer token before login traffic reached their instance.
No overload threshold was triggered. Recovery runs completed without errors.

## Permanent code changes

- `oldap_api/__init__.py`: startup no longer clears Redis. Each process loads
  project prefixes using one anonymous library Connection before readiness,
  then discards that connection/token. Requests retain independent authenticated
  connections. Startup now requires GraphDB and the anonymous principal.
- The explicit Flask CLI command `clear-object-cache` holds the normal writer
  gate with zero wait and invokes the library's isolated object-cache clear.
  Busy/uncertain ownership refuses the operation. Operators must quiesce readers
  too; the writer gate does not prevent stale read-side repopulation.
- Upload/tmp directory creation tolerates simultaneous worker initialization.
- Read tooling now accepts another loopback API port and samples every Gunicorn
  listener process. A supervisor runs the temporary configurations and cleans
  up only its own process groups. A test-only hook blocks non-read routes and
  identifies responding workers; it is not a production configuration.

No oldaplib source, GraphDB settings, production deployment, dependency version
or native LaunchAgent configuration was changed. The existing native API was
not restarted; it adopts the new initialization code on its next normal start.
Full object-cache invalidation is no longer implicit in future API restarts.
See the [maintenance procedure](README.md#worker-startup-and-explicit-cache-invalidation).
The cache-clear command itself was **not executed** against shared services.

## Experiment and qualifications

The additional service used `127.0.0.1:8100`; the existing API remained on 8000.
All configurations used Gunicorn `gthread`, four threads per worker, no preload,
30-second request timeout, and the same compact JSON behavior as the native API.
Thus increasing workers also increases total thread capacity. This compares
useful deployment configurations, not worker count in isolation from threading.

Each configuration ran the same closed-loop workflow mix as the previous load
test at **1, 8, 16 and 1 recovery reader**, for 30 seconds of offered work per
stage, followed by drain. Think time was 0.5–1.5 seconds. Fixed warm references,
anonymous permissions and the small existing Fasnacht dataset were reused.
Four-worker throughput is also constrained by this offered workload; 19.35
requests/s must not be interpreted as its maximum capacity. The prior native
Werkzeug test used different thread behavior and stage duration and is not the
baseline for the worker-count percentages above.

The initial serial four-worker preflight stopped after 800 successful reads
because the shared listener did not distribute every case to every worker.
No timed four-worker samples were taken in that attempt. The corrected
preflight uses up to 16 concurrent clients and requires full observed coverage.
Only the four-worker configuration was retried; valid one/two-worker results
were retained. All configurations were warm before timing, but warmup schedules
were not identical. This and the short ascending, unrepeated stages limit
statistical claims. A VM pilot should repeat and alternate configurations.

CPU measurements include JVM housekeeping and background clients. There is no
GraphDB query-queue attribution, no large HMB dataset, cold-cache scenario,
media transfer, browser rendering, or write traffic in this experiment. Redis
pools were not pushed to their 32-connection per-process limit.

## Operational boundary and next step

The current native launchd writer-recovery implementation explicitly rejects
child-process topologies and expects writers in its reviewed process inventory.
It must **not** be switched to Gunicorn for general write traffic on the basis
of this test. Before a permanent multi-process deployment, implement and test
whole-process-group supervision, writer identification, fencing, and recovery
for the chosen VM deployment. Existing writer-gate/restart tests passing does
not establish multi-worker crash-recovery correctness.

After that lifecycle work, compare two and four workers on the actual eight-vCPU
VM with the same benchmark, realistic HMB data, and database queue measurements.
Optimize remaining model/serializer CPU if single-request latency still needs
improvement. This experiment provides no reason to require a FastAPI rewrite
or an Enterprise purchase before those more targeted steps.
