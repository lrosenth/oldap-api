# Deployed Docker VM read acceptance — 2026-09-30

## Result and next decision

The deployed API passes the bounded anonymous read acceptance: **2,409 timed
requests**, all HTTP 200 and equal to their normalized per-run references.
Both runs preserve the same explicit named-graph fingerprint and the existing
API/GraphDB/cache container and service-process identities. No application
service was restarted, no worker setting changed, and no data was written.
The public HTTPS health endpoint returns 200; resource, sorted search and
25-resource summary smoke reads also match the VM-local response references.

The current **4-worker × 2-thread** configuration sustains about **16.1 requests/s
at 16 active readers**, with **232 ms median / 649 ms p95** using complete
25-resource metadata batches. This is a short closed-loop observation, not a
maximum-capacity figure or a claim about 16 simultaneous in-flight requests.

API CPU is about **2.13 cores**, GraphDB **0.33 cores**, and cache Redis **0.016
cores** at this stage. All four API workers consume CPU. Summed API RSS peaks
at **524 MiB**, GraphDB RSS near **1,871 MiB**. Shared memory can be counted more
than once in summed RSS. There is no evidence here of whole-VM CPU exhaustion
or a GraphDB CPU bottleneck, but these averages do not isolate query wait time,
short bursts, GIL contention, worker queues or unrelated production traffic.

**Next optimization:** profile per-request API/library CPU, prioritizing model
construction, deserialization and serialization for resources and summaries.
Earlier local profiles identify repeated model reconstruction, signature
inspection and project snapshot copying as candidates; this VM run does not
separately attribute those costs. Preserve request/user isolation and model
freshness. The Fasnacht datamodel read is also relatively expensive, but its
intentional fresh-read behavior must not be removed as an indiscriminate cache
optimization. Re-run this accepted VM catalog after a measured change.

An additional controlled worker comparison requires the documented maintenance
boundary. It was not performed during these live read tests. Neither asynchronous
FastAPI nor GraphDB Enterprise benefits can be inferred from this workload;
representative larger HMB data and direct query/queue evidence remain separate.

## Runtime and method

- User-deployed API `v0.2.29`, installed oldaplib `0.7.23`, GraphDB image `11.3.0`.
- Eight VM vCPUs, about 15.6 GiB RAM; no Docker CPU/memory quota on these three services.
- Existing Gunicorn arguments: four workers, two threads, 60-second timeout.
- Python benchmark runs on the Linux host against the private API container IP.
  Public proxy/TLS/WAN/browser and media-file transfer are excluded from timings.
- Anonymous `UnknownUser`, unchanged permissions and existing production data.
- Each of 17 cases: one discarded warmup, 12 serial samples. Then 30-second
  workflow stages with independent sessions and 0.5–1.5-second think times.
- Same fixed workflow mix as the laptop test: search + summaries, resource
  retrieval, archive navigation, structured full text, model and list metadata.
- HTTP durations include transfer but exclude JSON decoding/content hashing;
  workflow durations include those checks. Arrays are normalized as unordered;
  result ordering is not verified. Throughput includes stage drain and
  monitoring overhead. p95 uses nearest rank; serial p95 is the maximum of 12.
- Stop on response/content error or a request over five seconds; stop ramping
  above two-second stage p95. No stop threshold was reached.
- No writes, migrations, cache flush, recovery fault injection or integration
  fixtures. Normal read-side cache population and existing access logs remain.

## Two catalogs, kept separate

The first run exactly replays the private laptop request catalog. All 17 routes
return 200, but summary responses contain only **15 of 25** and **60 of 100**
requested resources. This is the endpoint's normal missing/unreadable omission
behavior; the read test does not distinguish those two causes.

For the second run, a normal anonymous sorted search selects 100 distinct
readable media resources on the VM. Only the summary request IRIs change;
actual returned sizes are verified as **25 / 100 / 25** (the last with delivery
metadata). All other requests retain their original inputs. Both catalogs and
raw runs remain private. Different data/hardware/thread counts mean neither run
is a causal before/after comparison against the laptop or the previous VM image.
No pre-deployment VM baseline exists in this experiment.
